# PhiTar v0.6: large native USTAR writer

**Native desktop preview, TAR creation only.** This feature is deliberately separate from the existing browser/archive UI. It uses a user-initiated native folder picker and destination-save dialog to write an **uncompressed USTAR `.tar`** to disk in small chunks.

## What changed

- Large TAR mode scans metadata-only using `planNativeFolder()` with a 2 GiB input cap, still restricted to 1,000 files, 2,000 directories and 20 directory levels.
- USTAR file headers are generated by the same validated code as PhiTar's ordinary TAR writer. Non-ASCII TAR paths, symlinks, unsafe native paths and unsupported file types are rejected before the output is opened.
- The Tauri filesystem plugin opens each regular file and reads at most **64 KiB at once**, writing it to a newly created TAR file. No whole-input or whole-output buffers are allocated by this code path.
- The destination must be **outside the source directory**, and `createNew` prevents overwriting existing archives. A newly created incomplete output is removed on most failures. Handles are closed after use.
- Capability additions apply **only to PhiTar's own desktop build kit**: `fs:allow-open`, `fs:allow-read`, `fs:allow-write` and `fs:allow-remove`. Tauri's dialog-selected session scopes still apply. No broad home/drive access.
- Existing **ZIP / TAR.GZ / small TAR** retain the 75 MiB input cap and normal browser behavior. This is not streaming ZIP or streaming gzip.

## Important limitations

- **PhiTar cannot yet inspect or extract TARs over 75 MiB.** Its existing archive reader remains bounded and in-memory. Use a mature system TAR utility or 7-Zip for extracting a large generated TAR.
- The new writer does not compute a streaming SHA-256 receipt or verify the created archive by rereading it. It writes POSIX USTAR and performs per-file metadata checks; external inspection or extraction remains necessary.
- No pause/cancel/resume, progress-by-byte tracking, encryption, signing or archive splitting. Progress displays completed files.
- No support for paths beyond USTAR's filename/prefix limits, extended PAX headers, symlinks or non-ASCII TAR filenames. Use ZIP mode within its normal limits for Unicode paths.
- Source-file replacement between scan/read steps remains a theoretical race. The app rechecks file type and size, but this is **not** a filesystem snapshot and cannot guarantee identical source bytes against concurrent modification.
- Tauri filesystem dialog behavior should be manually verified on Windows, Linux and macOS. CI compilation alone does not prove desktop interaction.

## Manual verification

1. Install the unsigned PhiTar desktop build on an isolated test machine; confirm the **Large TAR studio** appears only in Tauri, never on GitHub Pages.
2. Select a folder >75 MiB containing regular ASCII-named files (fewer than 1,000). Save to a **new** `.tar` path outside the source folder.
3. Verify the output using a trusted OS TAR reader, for example `tar -tf archive.tar` and extraction into an isolated temporary directory. Compare file bytes or checksums externally.
4. Repeat with tiny regular files, nested directories and an empty file; compare the output against known USTAR readers.
5. Test canceling both dialogs, attempts to overwrite an existing output, symlinks, over-depth paths, very large folders and invalid TAR Unicode names.
6. Force a source-file read failure; confirm the new partial output is removed. No existing user files should be modified.
7. Reconfirm the standard ZIP and TAR.GZ creation, inspection, and small TAR workflows still work in both browser and desktop editions.

## Next engineering steps

Add streamed TAR reading and extraction, then incremental SHA-256 (using a reviewed native digest implementation), cancellation, and robust cross-platform GUI tests. Implement streaming ZIP/ZIP64 and compressed TAR separately; neither is implied by this initial TAR writer.
